03 · Reglas de operación

Cinco reglas

regla 1
Puerta única de clientes
Todo reporte de cliente o partner entra por JF, que clasifica y deriva.
regla 2
Herencia
Trabajo de Falime sin commits ni PR que caiga en área de producto pasa a JF al 100% (incluye 023/#16). Lo que tenga PR abierto se termina o se traspasa de forma explícita.
regla 3
Gate de custodia
Cambios en claves de firma, keyset o RBAC de firma requieren review de Cristian antes de merge.
regla 4
Fuente única de licensing
backend/src/licensing es código de Guardian; Factory lo consume como librería, sin copias.
regla 5
CODEOWNERS
Todo PR que mueva ficheros entre áreas actualiza CODEOWNERS en el mismo PR.
Cambios que requieren a ambos departamentos: contratos-espejo motor↔backend (Redis keys, _IDENTITY_SQL, layer_keys) · formato del bundle/MANIFEST · api/internal.py · rotación de kid del keyset (+ gate Cristian) · copias de engine-extensions por release · alta de imagen nueva (5 ubicaciones).

05 · Cómo trabajamos

Ramas, PRs y Definition of Done

La convención completa vive en CONTRIBUTING.md (raíz del repo) y el template obligatorio en .github/PULL_REQUEST_TEMPLATE.md. Esto es el resumen con el porqué de cada regla.

ReglaCómoPor qué
main siempre instalableGitHub Flow: main es la única rama permanente. Todo entra por PR.Cualquier demo o instalación urgente sale de main sin preguntar "¿qué rama uso?". La lección de dev-fran.
Ramas cortasUna rama = una tarea, vida < 3 días. Nombres: NNN-descripcion (spec), fix/..., chore/.... Muere al mergear.Prohibido rama por persona o por país.
Títulos Conventional Commitstipo(scope): descripción — feat, fix, docs, chore, spec, refactor, test. Ej.: fix(presidio): fallar en voz alta cuando NLP degrada a regex (#63)El historial se lee solo y el changelog del release se arma gratis.
PR < 400 líneas de códigoUn PR = un propósito. Si crece, se parte en cadena de PRs. No mezclar refactor con feature. El tope no aplica a specs/planes SDD ni docs (specs/**, docs/**, *.md): son largos por diseño.Arriba de 400 líneas la review deja de encontrar defectos (evidencia empírica de estudios de code review).
Sin issue no hay PRTodo PR linkea su issue con Closes #NN y lleva label depto:guardian / depto:factory.Trazabilidad: cada cambio responde a un problema registrado, no a un impulso.
Review cruzada + gateAprueba el otro jefe técnico si toca su área o una costura. Cristian revisa obligatorio si toca claves/firma/auth (regla 3).Nadie se auto-mergea en territorio ajeno; la custodia de claves tiene dueño único.
Definition of Donepytest tests/ -q verde + docs afectadas en docs/docs/** actualizadas + make -C deploy check-docs verde.Doc desactualizada = bug de severidad alta: el producto se vende por su honestidad (regla desde la review de la 022).

06 · Ciclos de trabajo

Shape Up adaptado: 2 semanas, fecha fija

Se recorta alcance, nunca se mueve la fecha. Por qué: con 2 devs y deadline de producción en septiembre, la fecha fija fuerza a decidir qué importa; el alcance flexible evita el crunch.

1 · Shaping
Cristian, antes del ciclo
Brief de 1 página por apuesta: problema, solución a grandes rasgos, límites, no-metas, "done cuando". Template en Structure/guardian-metodologia/references/plantillas.md.
2 · Betting
Cristian + jefes, 30 min
Se decide qué apuestas entran. Lo que no entra no queda en backlog infinito: se re-apuesta el ciclo siguiente o se descarta.
3 · Building
Fran y Falime, autonomía total
Cada dev descompone su apuesta en tareas y ramas cortas. Cristian no microgestiona dentro del brief.
4 · Cooldown
2-3 días
Bugs, deuda, ADRs pendientes, demo corta de lo entregado entre los 3.
La operativa diaria no entra en apuestas: soporte Cámara, bugs de piloto y pedidos de clientes fluyen por Kanban aparte con límite de trabajo en curso. Así las apuestas no se contaminan y lo urgente no espera 2 semanas.

07 · Decisiones estructurales

Módulo, rama, repo o perfil — respuestas por defecto

Cada decisión de este tipo se escribe una sola vez como ADR (1 página) en docs/adr/. Si la duda ya tiene ADR, la respuesta es el link. Por qué: las decisiones no escritas se re-discuten cada mes y se pierden al rotar gente.

PreguntaRespuesta por defectoPor qué
¿Repo nuevo?Solo si despliega y versiona independiente con equipo propio. Hoy el único split aprobado es guardian-factory (deploy/).Repos separados que deben desplegarse juntos = monolito distribuido: coordinación de monorepo sin sus beneficios.
¿Plugin / complemento / integración nueva?Módulo dentro del monorepo con dueño en CODEOWNERS.Comparte código, tests y release sin coordinar versiones entre repos.
¿País nuevo (AR / ES / CO…)?Nunca rama por país.País = perfil de configuración (policy pack: PII local DNI/NIF/cédula, compliance, precios, idioma) en deploy/clients/. Decidido en ADR-0001. Agregar país = escribir un perfil, no mantener un fork.
¿Feature grande?Spec en specs/NNN-*/ (Spec-Kit, ya vigente) y luego ramas cortas por tarea.El proceso SDD ya demostró funcionar (013–031); no se inventa otro.

08 · La skill guardian-metodologia

Toda esta metodología, ejecutable con Claude

En Structure/guardian-metodologia/ (carpeta) y Structure/guardian-metodologia.skill (instalable). Encapsula departamentos, router, reglas, runbooks de instalación y release, convenciones de PR y plantillas de brief/ADR/issue/Slack.

Cómo instalarla

Cowork / app de escritorio: arrastrar el archivo guardian-metodologia.skill al chat y pulsar "Save skill".

Claude Code (CLI): copiar la carpeta al directorio de skills del usuario:

cp -r Structure/guardian-metodologia ~/.claude/skills/

Se activa sola: al pedir cosas de organización, PRs, issues, releases o instalaciones, Claude la carga y responde según esta metodología.

Qué pedirle (ejemplos)

• "Revisa este PR contra la convención" — verifica título, tamaño, issue, DoD, CODEOWNERS.

• "¿Esto va como módulo o repo? ¿Rama para Colombia?" — aplica las reglas del §07 y redacta el ADR.

• "Arma el brief del próximo ciclo" — lee los roadmaps y propone apuestas por dev.

• "Coordina la instalación del cliente X" — runbook: Fran congela versión → Cristian define compliance del país → Falime emite licencia (gate de Cristian si toca custodia) + perfil + bundle + instala.

• "Clasifica este issue" — router del §02, label depto:guardian / depto:factory.

Por qué una skill y no solo docs: los documentos se leen una vez; la skill se aplica en cada tarea. Fran y Falime pueden usarla igual que Cristian — las reglas son las mismas para los tres, y la fuente de verdad sigue siendo el repo (CONTRIBUTING.md, docs/adr/, este HTML).
